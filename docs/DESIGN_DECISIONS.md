# 设计决策记录（Design Decisions）

> 本文记录 Postbird 中**偏离直觉实现**的架构选择：每项写明采用了什么、放弃了什么、为什么，以及付出的代价。目标读者是审查者、贡献者与想把同类能力移植到别的 Agent 运行时的人。
>
> 行为规范见 [SECURITY.md](../SECURITY.md)，工具清单见 [README.md](../README.md#all-tools)，仓库约定见 [AGENTS.md](../AGENTS.md)。本文只解释「为什么」，不重复「是什么」。

记录方式参考了工程界常见的 ADR（Architecture Decision Record）习惯：**决策必须可被反驳**，因此每条都附替代方案和代价。状态标记为 `已落地` / `部分落地` / `已知取舍`。

---

## D1. 做成 DSH 原生 Cordis 插件，而不是独立应用或 MCP 服务

**状态：已落地**

- **采用**：`lib/index.js` 以 `apply(ctx)` 注册 22 个工具，`ctx.skills.registerProvider()` 注册技能；依赖声明为 `peerDependencies`（`@deepseek-ai/dsh-tools`、`@deepseek-ai/schemastery`）。
- **放弃**：独立 Electron/Web 应用；把能力拆成独立 MCP server 再由 DSH 连接。
- **理由**：Postbird 的价值在于「邮件理解 → 行动判断 → Office 交付」处在**同一个对话上下文**里。若做成独立应用，用户要在两个界面间搬运邮件和文件；若做成 MCP server，工具能复用，但「什么时候该用哪个工具」的工作方法会与工具分离，版本容易走散。DSH 的 "Everything is a Plugin" 允许工具、技能、配置同时注入宿主，是这个闭环最短的路径。
- **代价**：绑定 DSH 运行时，无法直接给 Claude Code / Cursor 等其它宿主使用；宿主 API 处于 Developer Preview，破坏性变更需要跟进。仓库里的 `demo/` 是静态演示页，不是可移植的运行时。
- **可移植性**：确定性逻辑集中在 `lib/*.js`，`lib/index.js` 只负责注册与参数适配；将来若要出 MCP 版本，可复用 `lib/` 而只重写注册层（参考 Inbox Zero 把邮件能力反向包成 `utils/mcp/email-tools.ts` 的做法）。

## D2. 工具与「怎么用工具」同版本发布

**状态：已落地**

- **采用**：技能文件随 npm 包分发在 `skills-zh/` 与 `skills/`，由 `lib/skills.js` 通过 `ctx.skills.registerProvider()` 注册进 DSH 技能注册表；安装器升级时**替换**技能目录而非合并（见提交 `f3823e8`）。
- **放弃**：让用户手动把 SKILL.md 复制到 `~/.dsh/skills/`；把用法说明只写在 README 里。
- **理由**：DSH 的技能加载器只扫描固定目录，插件自带的 `skills/` 默认不会被发现。若靠手工复制，插件升级后工具行为变了、技能说明还是旧的，模型会按过时流程调用工具——这是一类很难排查的故障。注册成 provider 后，工具与使用说明共享同一个版本号。
- **代价**：依赖 `ctx.skills.registerProvider()` 这个宿主能力；用户自己在 `~/.dsh/skills` 放的同名技能可以覆盖插件版本，这是**刻意保留**的逃生口，但也意味着行为可能被本地文件改变。
- **取舍**：`skills-zh/` 为 DSH 中文适配版并优先，`skills/` 保留上游英文版。中英双份带来同步成本，换来的是中文触发条件更准（技能是否加载取决于 `description` 写得是否贴合用户说法）。

## D3. 发信强制两阶段：预览 → 显式确认

**状态：已落地**

- **采用**：`office_mail_send` 只接受 `office_mail_preview` 返回的 `previewId`，且必须显式 `confirm: true`；预览带 TTL（默认 60 分钟）自动作废；预览内容变更必须重新生成；`context_reply` / `reply_draft` / `collection_track` 等工具一律不发送邮件。
- **放弃**：单工具 `send_email(to, subject, body)` 直接投递；让 Agent 在提示词里「记得先问用户」。
- **理由**：邮件是不可撤销的外部动作，而 Agent 面对的是**不可信输入**（邮件正文、CSV 单元格都可能含提示注入）。把确认放在提示词里，等于把安全边界寄托在模型的注意力上；放在工具协议里，则模型无论怎么想都得先产出预览。这也是我们与通用邮件 MCP 最本质的区别：它们通常把 `send_email` 作为一个普通工具暴露，由宿主决定是否弹审批。
- **代价**：多一次往返，批量场景需要用户看一次样本；`previewId` 是有状态的，跨会话失效是刻意设计（防陈旧预览被复用）。
- **补充护栏**：默认 `mode: "draft"` 只写 `.eml` 文件，未配置 SMTP 凭据时**物理上无法发送**；单批上限 50、24h 滚动上限 200、最小间隔 1500ms、`allowDomains` 域名白名单、收件人去重、缺模板字段整批硬失败。

## D4. 收件侧严格只读，不提供删除/移动能力

**状态：已落地**

- **采用**：IMAP 一律 `BODY.PEEK`，绝不置 `\Seen`；不写旗标、不移动、不删除；`office_inbox_clean` 只输出建议清单与 `List-Unsubscribe` 链接，且链接被视为不可信输入、不由插件请求。
- **放弃**：自动归档、自动退订、自动标记已读这类「顺手」的自动化。
- **理由**：读操作一旦产生副作用，Agent 的一次误判就会改变用户邮箱的真实状态，而且难以回滚。把收件侧做成纯函数式读取，用户才能在自己的邮箱客户端里保留最终处置权。
- **代价**：Inbox Zero 那类「自动清空收件箱」的爽感没有了；清理场景需要用户自己动手。这是**主动选择的能力缺口**，不是遗漏。

## D5. 每个判断都必须能回到原文出处

**状态：已落地**

- **采用**：分诊结果附命中的规则证据；`office_action_radar` 的行动项带来源；`office_attachment_ask` 对 PDF / DOCX / PPTX / XLSX / 文本分别返回**页、段落、幻灯片、工作表行、文本行范围**；`SKILL.md` 的 output contract 明确要求区分「确定性抽取」与「Agent 解读」，禁止编造截止时间、发件人、引用或发送成功。
- **放弃**：只让模型读全文然后自由总结。
- **理由**：校园办公场景（奖学金材料、报名核对、导师要求）里，一条错误的「某某没交」或虚构的截止日期会造成真实后果。可追溯性比流畅度重要。确定性规则负责给出可复核的事实，语义润色交给 Agent 并标注为解读。
- **代价**：输出更啰嗦；确定性规则对复杂语义会漏判，因此保留人工校正（`manualStatus`、`unscheduled` 标记、低置信度复核队列）。

## D6. 数据驱动路径强制 workDir 隔离

**状态：已落地，且经过真实漏洞修复**

- **采用**：收件人表（CSV/JSON）里的附件路径、pptx 的 `imagePath`、归档导出目录，解析后必须落在 `workDir` 内，逃逸即拦截；输出文件默认拒绝覆盖，需显式 `overwrite: true`；文件名统一清洗去重。
- **理由**：收件人表通常来自外部（学生名单、他人提供的表格），是**最主要的攻击向量**。恶意单元格一旦能把 `~/.ssh/id_rsa` 或 `../../.env` 变成附件，就是直接的数据外泄。
- **实证**：v1.1.1 修复了 4 个已记录漏洞——邮件附件路径逃逸（高）、pptx imagePath 路径逃逸（高）、CRLF 头注入伪造 Bcc（中）、缺少发送总量护栏（中）。修复与回归用例写在 [SECURITY.md](../SECURITY.md#已修复漏洞) 与 `tests/e2e.mjs`。
- **代价**：跨目录引用附件时必须先把文件放进工作目录；这对「附件散落在下载文件夹」的用户不够方便，但比默认信任路径安全。

## D7. 凭据只走环境变量

**状态：已落地（已知取舍）**

- **采用**：`DSH_IMAP_PASS` / `DSH_SMTP_PASS`（可用 `imapPassEnv` / `smtpPassEnv` 改名）；不写配置文件、不进审计日志、预览文件与草稿文件；审计日志只记时间戳、收件地址、主题、投递结果与 `.eml` 路径。
- **理由**：配置最小、审计面最小，且不会被打包进仓库或插件数据目录。
- **已知取舍**：多账号切换不便，改密码需要改环境并重启；相比 DSH 生态里把凭据存进宿主凭据库（`0600` 权限、设置页登录、每次操作现读）的方案，易用性偏弱。这是当前最值得改进的一项，见文末「下一步」。

---

## D8. 技能描述写触发条件，不写功能介绍

**状态：已落地**

- **采用**：`skills-zh/*/SKILL.md` 的 `description` 写「当用户提到……时加载」，`whenToUse` 还明确写了**什么时候不要加载**（纯文档排版改用 DSH 内置 office 技能）；根目录 `SKILL.md` 提供英文规范版与 output contract。
- **理由**：技能是否被加载取决于宿主对 description 的匹配，而不是功能列表。写清触发边界能减少误加载和与宿主内置技能的冲突。
- **代价**：description 偏长；中文适配版与上游英文版需要保持行为一致。

---

## D9. 索引只存元数据与短摘要

**状态：已落地**

- **采用**：`~/.dsh/office/mail/index.jsonl` 只存时间/发件人/主题/附件清单与短摘要（默认 300 字符）；完整正文仅在 `contextMode: full` 时按需经 `BODY.PEEK` 读取，只存在于当前进程内存，受 `maxThreadCharsPerMessage` / `maxThreadMessages` 限制，不写回索引；`.eml` 导出是唯一把正文全文落盘的路径，且必须用户显式要求。
- **理由**：邮件正文是敏感数据，也是提示注入载体。最小化落盘同时缩小了泄露面与注入面。
- **代价**：只靠摘要回答不了复杂线程问题，需要显式切 full 模式，多一次 IMAP 往返。

---

## D10. 工具输出进入 Agent 上下文，边界写清楚而不是假装隔离

**状态：已落地**

- **采用**：在 README 与 SECURITY.md 明确写出「工具返回给 DSH 的文本会进入当前 Agent 上下文，其存储与模型处理路径取决于使用者选择的部署与模型」，并在处理敏感邮件前提示确认运行时。
- **理由**：很多「本地优先」项目把本地存储说成端到端隐私，但对「内容仍会送给模型」避而不谈。把边界讲清楚，才是可被审查的安全声明。
- **代价**：说实话会削弱营销话术，但换来的是可信任。

## 下一步（诚实清单）

按性价比排序，当前已知可改进处：

1. **凭据与分发**：迁到 DSH 凭据库 + 设置页登录，发布 npm 包并上架插件市场，去掉手写 `setup` 脚本（对照 D7）。
2. **工具风险元数据**：为 22 个工具补结构化 `readOnlyHint` / `destructiveHint` / `idempotentHint`，让宿主能自动分级审批，而不只依赖工具描述里的文字约定。
3. **输出校验闭环**：`office_docgen` / `office_pptx` / `office_sheet` 生成后增加「渲染 → 检查 → 再报告完成」的验证步骤（官方 Agent Skills 的 docx 技能即如此）。
4. **规则可配置与持久看板**：把静态技能里的分诊规则外置为可编辑数据，并补「等我回 / 等对方回」的持久状态。
5. **对外供给能力**：把 `office_*` 反向包成 MCP server，让其它 Agent 宿主也能调用（对照 D1 的可移植性说明）。

这些都不改变本文已落地决策的安全姿态；第 2、3 项属于把既有防护进一步结构化。
